# photo-crop-band (사진 처리 결과에 검은·빈 띠가 생기는 문제 조사)

> pm-dev-pipeline 기획서(조사). PM 이 쓰고 개발자가 읽는다.

## 목표
일부 사진을 우표로 만들 때 처리 결과(1200px 사진, 300px 썸네일)에 그림이 왼쪽 위 약 83% 만 차고 오른쪽에 검은 띠, 아래에 빈 띠가 생기는 원인을 찾고, 고칠 방법을 **제안**한다.

## 배경 (PM 측정, 2026-11-02)
- 시뮬레이터(iPhone 17, iOS 26.5) 앱 폴더의 저장 파일을 직접 열어 확인함. 화면 표시 문제가 아니라 **저장된 파일 자체**가 깨짐
  - 깨진 우표 2장: 11-07(생성 16:08), 11-05(생성 14:28). 사진 1200×1200, 썸네일 300×300 크기는 맞음. 내용이 약 250/300 만 차고 오른쪽 검정, 아래 빈 띠(흰색/투명으로 보임)
  - 같은 날 시뮬레이터에서 만든 11-01·10-31, 실기기에서 만든 11-02 는 정상
- 사용자 답: 깨진 두 장은 **아이폰 카메라 원본**(다른 기기에서 찍어 시뮬레이터 사진 보관함으로 옮긴 사진)
- 시뮬레이터 사진 보관함 원본 위치(읽기만): `~/Library/Developer/CoreSimulator/Devices/97B3ED6B-67B6-4451-9F97-85BED7809BF7/data/Media/DCIM/100APPLE/` — HEIC 1개, JPG 5개. 어느 파일이 어느 우표인지는 알 수 없음
- PM 추정(확인 안 함): 83% 는 원본 정보에 적힌 크기와 실제 디코딩된 이미지 크기가 다를 때의 비율과 비슷함(예: 4032 → 3360). 또는 EXIF 회전·HDR(게인맵)·10비트 등 특정 형식과 관련
- 같은 날 별건: 시뮬레이터 테스트 프로세스에서 처음 하는 HEIC 디코딩이 검정으로 나오는 현상(PR #13, 테스트만 고침). 관련 있는지도 확인할 것
- 사진 처리 코드: `PiecePost/Media/PhotoProcessor.swift`. 불변 규칙 5

## 완료 기준
1. 원인을 근거와 함께 적는다(측정과 추정 구분). 보관함 원본으로 재현되는지(어느 원본에서, 어떤 조건에서) 확인한다. 확정 못 하면 "찾지 못함" 과 아직 안 본 것을 적는다
2. 재현되면 그 원본의 특징(크기 정보·실제 디코딩 크기·EXIF 방향·색 공간·비트 깊이·HDR 여부 등)을 적는다
3. 고칠 방법을 제안한다. 다른 형식 사진(편집 사진, 세로·가로, JPG/HEIC, 작은 사진)에 영향이 없는지, 불변 규칙 5 를 지키는지 적는다
4. 재현용 단위 테스트를 어떻게 만들 수 있을지 제안한다 (사용자 사진을 저장소에 넣지 않는 방법으로)
5. **이번 조사에서는 커밋하지 않는다**

## 지켜야 할 것
- 사용자 사진 원본은 **읽기만** 한다. 저장소·작업 트리·리뷰 파일에 사진 파일이나 사진 내용 설명을 넣지 않는다. 재현에 복사가 필요하면 세션 임시 폴더에만 두고 끝나면 지운다
- 리뷰 파일에는 사진의 기술 정보(크기·형식·방향 등)만 적는다. 위치(GPS)·촬영 기기 일련번호 같은 메타데이터 값은 적지 않는다
- 시뮬레이터 앱 데이터·설정 변경·초기화 금지

## 수정 (2026-11-02 사용자 결정: 안 A + 재현 테스트, 별도 작은 PR)
1. `origin/develop` 에서 `fix/photo-crop-band` 브랜치. 조사 작업 트리에서 `git switch -c fix/photo-crop-band origin/develop` 로 만들어도 됨
2. 조사 결과의 안 A: `PhotoProcessor` 에서 `CGImage.cropping(to:)` 를 쓰지 않고, 회전된 원본을 1200px 캔버스(썸네일은 300px)에 가운데 정사각형이 캔버스를 채우도록 위치·배율을 정해 한 번에 그린다. 왜 바꾸는지 짧은 주석
3. 불변 규칙 5 유지: 원본에서 한 번만 자르고(1:1) 줄이고(1200px, 작은 원본은 키우지 않음) HEIC 0.8, 썸네일 300px. 사진 메타데이터·HDR 는 남기지 않음(기존 결정)
4. 재현 테스트: 테스트 안에서 합성한 HEIC(방향 6, 사분면 서로 다른 색)를 처리해 결과의 네 모서리·가장자리 색이 기대와 같은지(검은·빈 띠가 없는지) 확인. 방향 8 도 함께. 사용자 사진은 쓰지 않음
   - 가능하면 고치기 전 코드에서 이 테스트가 실패하는지 먼저 확인해 보고서에 적는다(테스트 프로세스에서 재현되는지 미확인이었음). 실패하지 않아도 테스트는 남긴다
5. 커밋마다 테스트가 통과해야 하므로, 고치기 전 실패 확인은 커밋하지 않은 상태에서 하고 결과만 보고서에 적는다. 커밋은 (1) 이 문서 (2) 수정 + 재현 테스트 순서. 중간 커밋은 단위 테스트, 마지막 커밋은 전체(UI 포함)
6. 로컬 커밋까지만, 푸시·PR 금지, Co-Authored-By 금지
7. 완료 보고에 사용자 실기기 확인 항목을 적는다: 실기기에서 세로로 찍은 사진으로 우표 만들기 → 띠 없음
