# sync-account-status (iCloud 계정 상태 처리)

> pm-dev-pipeline 기획서. PM 이 쓰고 개발자가 읽는다. 구현 방법보다 **무엇이 되어야 하는지**를 쓴다.

## 목표
iCloud 가 꺼져 있거나, 잠시 쓸 수 없거나, 용량이 부족하거나, 다른 Apple ID 로 바뀌어도 우표는 기기에 안전하게 남는다. 한 계정의 우표가 다른 계정에 올라가지 않고, 원래 상태로 돌아오면 다시 동기화된다.

## 배경
- `docs/system-design.md` 5장(iCloud 상태별 동작), `docs/tasks/01-sync-spike.md` S9
- 지금은 임시 처리: `StampSyncEngine.handleAccountChange` 가 로그와 상태 문구만 바꾸고, 계정 전환 뒤에도 엔진이 계속 돈다. 앱 시작 때 계정 상태(`iCloud 계정: …`)는 로그만 남긴다. `failedRecordDeletes` 는 로그만 남긴다
- 2026-11-02 사용자 결정
  - 계정이 다른 Apple ID 로 바뀌면: 미업로드분은 로컬에 두고 **동기화를 멈춘다**. **원래 계정으로 돌아오면 재개**한다. 새 계정으로 넘어가는 방법은 실제 화면(S04) 작업 때 정한다
  - 로그아웃했다가 **다른** Apple ID 로 로그인하면: 계정 변경과 같게 처리한다 (마지막으로 동기화한 계정을 기억해 비교). 같은 계정으로 다시 로그인하면 미업로드분을 올린다 (기존 합의)
  - 계정 상태가 `temporarilyUnavailable`·`couldNotDetermine` 이면: **오프라인처럼** 처리한다. 로컬 저장, 업로드 대기 유지, 재시도는 엔진에 맡김. 상태 표시는 "iCloud 일시 사용 불가"

## 완료 기준
판정할 때 하나씩 대조한다.

**계정 꺼짐·로그아웃 (S9)**
1. 앱 시작 때 계정 상태가 `noAccount`·`restricted` 이거나, 엔진이 로그아웃을 알리거나, 저장이 `notAuthenticated` 로 실패하면 상태가 "iCloud 꺼짐"이 된다. 우표 만들기·수정·삭제는 오류 없이 로컬에 저장되고 업로드 대기로 남는다
2. 같은 계정으로 다시 로그인하면(엔진의 로그인 알림, 또는 앱 시작 때 `available` + 기억한 계정과 같음) 상태가 정상으로 돌아오고, 업로드 대기 우표가 올라간다

**계정 변경 (다른 Apple ID)**
3. 마지막으로 동기화한 계정을 기기에 기억한다. 처음 동기화할 때(기억한 계정이 없을 때) 지금 계정을 기억한다
4. 엔진이 계정 전환을 알리거나, 로그인·앱 시작 때 지금 계정이 기억한 계정과 다르면 상태가 "계정 변경됨"이 되고 동기화를 멈춘다
   - 멈춘 동안 어떤 우표도 서버로 보내지 않는다 (새 계정에 올라가지 않음)
   - 멈춘 동안 새 계정에서 받은 변경을 로컬에 반영하지 않는다 (두 계정 데이터가 섞이지 않음)
   - 로컬 우표·사진·업로드 대기 표시는 그대로 남는다. 멈춘 동안 만들거나 고친 우표도 로컬에 저장되고 업로드 대기로 남는다
5. 원래 계정으로 돌아오면(엔진 알림 또는 앱 시작 때 확인) 상태가 정상으로 돌아오고, 보내기·받기를 재개한다. 업로드 대기 우표가 올라가고 서버 변경을 받는다. 전체를 다시 받게 되더라도 로컬 우표가 지워지거나 중복되지 않는다
6. 기억한 계정 정보는 로그에 남기지 않는다. 로그에는 `계정 변경됨, 동기화 멈춤`·`원래 계정으로 돌아옴, 동기화 재개` 같은 상태만 남긴다

**일시 사용 불가**
7. 계정 상태가 `temporarilyUnavailable`·`couldNotDetermine` 이면 상태가 "iCloud 일시 사용 불가"가 된다. 동작은 오프라인과 같다: 로컬 저장, 업로드 대기 유지, 재시도는 엔진에 맡김. "iCloud 꺼짐"으로 보이지 않는다
8. 계정 상태가 `available` 로 돌아오면(엔진 알림, 다음 앱 시작, 또는 포그라운드 진입 때 확인) 상태가 정상으로 돌아온다

**용량 부족**
9. 저장이 `quotaExceeded` 로 실패하면 상태가 "용량 부족"이 되고 로컬 데이터와 업로드 대기를 유지한다 (CLAUDE.md 판단 분기)
10. "용량 부족" 상태에서 앱이 포그라운드로 들어오면 업로드 대기 우표를 한 번 다시 보낸다 (설계 문서 5장). 성공하면 상태가 정상으로 돌아온다. 같은 포그라운드 진입 한 번에 여러 번 보내지 않는다

**삭제 실패 (`failedRecordDeletes`)**
11. 삭제 실패도 CLAUDE.md 판단 분기를 따른다: 네트워크 오류 → 삭제 대기 유지(재시도는 엔진), `quotaExceeded` → 9번과 같음, `notAuthenticated` → 1번과 같음, `unknownItem`(서버에 이미 없음) → 삭제 성공과 같게 로컬 행·사진 파일 삭제. 그 밖의 코드는 로그를 남기고 삭제 대기를 유지한다 (처리 방식은 정하지 않음)

**상태 표시·문서·검증**
12. 시험 화면의 동기화 상태에 "계정 변경됨", "iCloud 일시 사용 불가"가 보인다. 다른 화면 변경은 하지 않는다
13. `docs/system-design.md` 5장 표에 위 결정(계정 변경 시 멈춤·원래 계정 재개, 로그아웃 후 다른 계정 = 계정 변경, 일시 사용 불가 = 오프라인처럼)을 반영한다. AGENTS.md "남은 작업"에서 계정 상태 항목을 빼고 "이미 정한 결정"에 더한다. `README.md` 상태 표를 갱신한다. **`CLAUDE.md` 는 고치지 않는다** (PM 이 사용자 승인 뒤 같은 브랜치에 커밋)
14. 계정 비교·상태 결정·용량 부족 재시도 한 번 규칙처럼 CloudKit 없이 확인할 수 있는 규칙은 단위 테스트가 있다
15. 프로젝트 CLAUDE.md 의 검증 절차를 통과한다 (중간 커밋은 단위 테스트만, 마지막 커밋은 UI 테스트까지 전체)
16. 완료 보고에 사용자 확인 순서를 체크리스트로 적는다 ("사용자 확인 필요"): S9(로그아웃 상태에서 생성 → iCloud 꺼짐, 로컬 저장), 같은 계정 재로그인 → 업로드, 계정 변경(두 번째 Apple ID 가 있을 때만, 없으면 "확인 못 함"으로 표시). 받기 확인은 실기기에서 하거나 시뮬레이터는 앱 재실행으로 한다(시뮬레이터는 원격 푸시를 못 받음)
